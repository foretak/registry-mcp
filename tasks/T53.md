## A. `core/models.py`

### A1. The two models

Insert **immediately after `LeiRecord`** and before whatever follows it, so the GLEIF pair sits
together and the hunk is far from any other task's.

```python
class ParentLink(_Base):
    lei: str | None = None
    legal_name: str | None = None
    jurisdiction: str | None = None
    registration_status: str | None = None
    corroboration_level: str | None = None
    reporting_exception: str | None = None
    source_url: str | None = None

class ParentBlock(_Base):
    direct: ParentLink | None = None
    ultimate: ParentLink | None = None
    provenance: SourceRef
    notes: list[str] = []
```

and `CompanyReport.parents: ParentBlock | None = None`, always present per D-004, `null` on every
lookup that did not ask for it. **Place it immediately after `CompanyReport.lei`.** Do not widen
either model: **`entity.category`, `relationship.status`, `relationship.periods`, the exception's
`category` and the exception's `reference` are all declined by name in D-047(a)** — a field you want
is a `DECISIONS.md` entry, not an implementer's call (D-042(g)).

### A2. The invariant, enforced not assumed

Within one `ParentLink`, **`lei` and `reporting_exception` are mutually exclusive, and at least one
of them is populated.** Write it as a Pydantic model validator that raises, not as a docstring —
this is the D-011 contract of the whole block and it must be impossible to construct a link that
says both or neither. Test both violations.

### A3. What the field descriptions must carry, in substance

- **`ParentBlock` class docstring** — the two-level nullability, D-047(a)'s: an **absent**
  `CompanyReport.parents` means not asked for, or the fetch failed (a `notes` sentence on the report
  says which); a **present** block whose `direct` and `ultimate` are both `None` means GLEIF holds no
  LEI for this entity at all, so there is no Level 2 to hold either. And the sentence the whole block
  hangs on: **GLEIF Level 2 reports the *accounting consolidating* parent — the entity that
  consolidates this entity's accounts — which is not the same as the majority shareholder, and
  neither implies the other.** The wire word is `IS_DIRECTLY_CONSOLIDATED_BY`; say so.
- **`direct` / `ultimate`** — two independent sides that can disagree in kind. In a 600-record
  Swedish sample, 9 records disclosed a direct parent and 10 disclosed an ultimate one, so one
  excepted the direct side while reporting the ultimate. Never collapse them, never derive one from
  the other.
- **`lei`** — the parent's own 20-character LEI. It is a lookup key **for GLEIF**, and the caller can
  feed the parent's `registeredAs` (which we do not carry) to nothing — say plainly that the way to
  walk up a group from here is `lookup_company` on the parent's own national identifier where the
  caller has it, and that Norway additionally publishes `CompanyReport.parent_id` on the *first*
  round trip from Enhetsregisteret, which is a different register's answer to a neighbouring question
  and is not reconciled against this one (D-018).
- **`legal_name`** — the parent's legal name as GLEIF publishes it, verbatim, never reconciled.
  **Bound by D-028(1)**: never a lookup key, never an index, never searchable, never in a log
  (D-040). The description must say why the binding exists rather than just asserting it: GLEIF
  holds **126,936** records with `entity.category: SOLE_PROPRIETOR` whose `legalName` is routinely a
  natural person's name, and although no sole-proprietor *parent* was observed (0 of 30 sampled
  sole proprietors had any direct child), nothing in RR-CDF 2.1 forbids one.
- **`registration_status`** — the **parent's** `registration.status` (`ISSUED`, `LAPSED`, …),
  carrying the same warning `LeiRecord.registration_status` already carries: a `LAPSED` LEI means the
  entity stopped renewing it and is **not** evidence of insolvency. Point at that field's description
  rather than restating it in full.
- **`corroboration_level`** — GLEIF's `registration.corroborationLevel` on the *relationship* record,
  verbatim: `FULLY_CORROBORATED`, `PARTIALLY_CORROBORATED`, `ENTITY_SUPPLIED_ONLY`. Measured over 31
  disclosed relationships: 10 / 11 / 10. **Roughly a third of all disclosed parent links are the
  filer's own assertion that nobody has checked** — say that, in terms, because it is the reason this
  field costs a request. `None` on the exception side, where there is no relationship record.
- **`reporting_exception`** — the reason the entity gave for not reporting a parent, from GLEIF's
  closed `ExceptionReasonEnum`: `NO_LEI`, `NATURAL_PERSONS`, `NON_CONSOLIDATING`, `NO_KNOWN_PERSON`,
  `NON_PUBLIC`, and five deprecated-since-2022-03-01 values retained for compatibility
  (`BINDING_LEGAL_COMMITMENTS`, `LEGAL_OBSTACLES`, `DISCLOSURE_DETRIMENTAL`, `DETRIMENT_NOT_EXCLUDED`,
  `CONSENT_NOT_OBTAINED`). Relayed verbatim, national-vocabulary-in-values (D-042(g)). **The
  description is the most important string in this task and it must carry all four of these:**
  1. GLEIF's own gloss — `NATURAL_PERSONS` means *"the entity is controlled by a natural person(s)
     without any intermediate legal entity"*; `NON_CONSOLIDATING` means *"controlled by legal entities
     not subject to consolidation"*; `NO_KNOWN_PERSON` means *"no known person(s) controlling the
     entity (e.g. the entity is controlled by diverse shareholders)"*.
  2. **It is a category word and never a name.** Nothing beyond the word is available and nothing
     beyond the word would be relayed if it were (D-028).
  3. **It is the entity's own stated reason and it is not verified by GLEIF or by us.**
  4. **It is not applied consistently between filers**, with the measured proof: `NATURAL_PERSONS` is
     **49 of 57** Norwegian ultimate-parent exceptions (86%) and **28 of 60** British ones (47%), and
     **EQUINOR ASA (`OW6OFBNCKXC4US5C7523`), 67% owned by the Norwegian State, reads
     `NATURAL_PERSONS`** while DNB, Telenor and Tesco — in the same position at the top of their own
     groups — read `NON_CONSOLIDATING`, and BP, Ericsson and Carillion read `NO_KNOWN_PERSON`.
- **`source_url`** — the exact GLEIF URL that returned *this side*. This is D-046(d)'s
  disclose-the-leg rule: the block has one `provenance`, and each side names its own URL.
- **`provenance`** — one `SourceRef` for the whole fan-out. `source` names GLEIF, `license` is
  **`"CC0 1.0"`** (GLEIF's Terms of Use put all LE-RD, Level 2 included, under CC0 — checked
  2026-09-09), `source_url` is `https://api.gleif.org/api/v1/lei-records/{lei}`, `fetched_at` is the
  moment the last leg returned. **Never imply endorsement and never describe `registry-mcp` as a
  GLEIF service** (D-026(c)).
- **`notes`** — must always name the URLs actually fetched, the same way `LeiRecord.notes` names the
  `registeredAs` string that was sent, so a `None` is legible rather than silent. On the exception
  side it must also carry the "this word is the filer's, unverified, and inconsistently applied"
  sentence, because a caveat that lives only in a schema description does not travel into a rendered
  answer (D-046(a)'s reasoning).

## C. `core/gleif.py` — the fetcher

### C1. The discovery step is the `lei` search, shared and never repeated

`fetch_lei` already caches the raw search body under `{COUNTRY}:{registry}:lei:{id}` as
`{"queried": [...], "response": <raw GLEIF body>}`. **The parents path reads that entry, and
populates it through the same code path when it is cold.** Factor the search out of `fetch_lei` into
one internal coroutine that both callers await, so that:

* a lookup asking for **both** `lei` and `parents` makes **exactly one** `lei-records` search request;
* a lookup asking for only `parents` still fills the `lei` cache entry as a side effect, which is
  correct — it is the same fetch;
* the two never race.

**This is the hazard, and it is D-043(h)(3) verbatim in a new place.** `lookup_with` runs attachment
methods with bounded concurrency, so a naive implementation makes two identical searches on a cold
cache, and the tests pass because both succeed. **Assert the request count**, do not assume it.

### C2. Choosing the endpoint — read the link key, never guess

The search response's `data[0].relationships` carries `direct-parent` and `ultimate-parent`, and
**their `links` keys are the discriminator**:

| `links` key present | Meaning | Fetch |
|---|---|---|
| `reporting-exception` | no parent reported | `GET {that URL}` → `data.attributes.reason` (and `category`, which you do **not** carry) |
| `lei-record` (with `relationship-record`) | a parent is disclosed | `GET {lei-record URL}` → the parent's own Level 1 record, **and** `GET {relationship-record URL}` → `data.attributes.registration.corroborationLevel` |

**Use the URLs GLEIF puts in `links`. Do not construct them from a template**, for D-046(b)'s reason
one country over: a hardcoded path works until it does not, and the failure looks exactly like "no
parent".

So the fan-out is **one extra request per side on the exception path (2 total) and two per side on
the parent path (4 total)**, run concurrently. Measured hit rates: a disclosed direct parent on
19/600 NO, 12/600 GB, 9/600 SE — so the 4-request case is ~3% of lookups and the expected cost is
**2.06 extra requests**.

### C3. The trap — `?include=direct-parent,ultimate-parent` is not used

GLEIF accepts `include=direct-parent` and `include=ultimate-parent` on `lei-records` (every other
relationship path is a **400**, *"Include paths should contain only allowed ones"*) and returns an
`included` array — **whose members are resource identifier objects with `type` and `id` and no
`attributes` at all.** It fetches nothing. It grows the exception-path body from 3,528 to 4,573
bytes (+30%) to carry two stubs. **D-047(a) names this as the single thing an implementer will get
wrong**: the code compiles, the response looks like a JSON:API compound document, and `legal_name` is
`null` forever. `grep -rn "include=direct-parent\|include=ultimate-parent" src/` must return nothing
outside a comment explaining this paragraph, and that grep is a done-check.

### C4. Fields, exactly

From the **parent's Level 1 record** (`/…-parent`): `attributes.lei` → `lei`,
`attributes.entity.legalName.name` → `legal_name`, `attributes.entity.jurisdiction` → `jurisdiction`,
`attributes.registration.status` → `registration_status`. **`entity.status` is never read**, here or
anywhere (D-045(e)); neither is `entity.category`.

From the **relationship record** (`/…-parent-relationship`):
`attributes.registration.corroborationLevel` → `corroboration_level`, and **nothing else**.
`attributes.relationship.status` was `ACTIVE` on 31/31 and `attributes.registration.status` was
`PUBLISHED` on 31/31 — constants, struck by D-047(a). `attributes.relationship.periods` is struck too;
name the `RELATIONSHIP_PERIOD` start date in a `notes` sentence as the one thing a caller loses, and
do **not** model it.

From the **reporting exception** (`/…-parent-reporting-exception`): `attributes.reason` →
`reporting_exception`, and **nothing else**. **`attributes.reference` is never read, never mapped and
never relayed** — it is `[1,*]` free text of up to 500 characters per entry, it was `null` on 117 of
117 exceptions fetched, and D-047(a) rules it out under D-042(e)'s free-text rule. No model field, no
mapper branch, no `notes` sentence that could carry it.

### C5. Failure and nullability

- GLEIF holds **no LEI** for the entity (`total == 0` on the search) → a **present** `ParentBlock`
  with `direct=None`, `ultimate=None`, a real `provenance`, and a `notes` sentence saying GLEIF holds
  no LEI so there is no Level 2 either. This is the answer, not an absence.
- **A failed leg degrades one side, never the block.** If the exception fetch for `direct` 500s but
  `ultimate` succeeds, the block is present, `direct` is `None`, and a `notes` sentence names the leg
  that failed. Only a failure of the *search itself* raises `RegistryError(UPSTREAM_ERROR)`, which
  `lookup_with` turns into an absent block plus a report-level note, with the lookup still succeeding
  (D-042(b)).
- `links` carrying **neither** key was **0 of 1,800** records. Handle it as `None` for that side with
  a note, and do not raise.

### C6. Cache

One key for the composed answer: **`{COUNTRY}:{registry}:parents:{id}`**, kind `parents` in the third
segment so `core/cache.py`'s table finds it. Never a second key per side. `status="not_found"` when
GLEIF holds no LEI, `"ok"` otherwise. `provenance.cached` describes **this** entry, not the `lei` one.
