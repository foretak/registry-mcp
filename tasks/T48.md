## The four facts (D-045(f)), each with the question it must answer for a Sonnet

1. **The SMP resolution route for a `0192:` participant.** Given `0192:923609016`, exactly how does one find
   whether the participant is registered and what it accepts: the SML/DNS lookup (hash of the participant id →
   SMP host), the SMP's `/{participantId}` service-group URL and its XML, or the Peppol Directory's REST search.
   Is it HTTP at all from a plain client with no Peppol certificate? Which of these does Digdir/DFØ recommend for a
   *lookup* (not an exchange)? One live resolution of Equinor with the request and the trimmed response.
2. **The Peppol Directory's query endpoint and response shape.** `https://directory.peppol.eu/search/1.0/json?
   participant=…` or whatever it actually is today; the JSON fields; whether Norwegian ELMA participants appear
   there at all (ELMA is a national registry — is it published into the Directory, or only into the SML?); rate
   limits and terms printed on the page.
3. **Terms and rate limits from Digdir / DFØ.** Whether ELMA's lookup interface is public and what its terms
   say about automated lookups; the licence, if any; whether there is an NLOD-style statement. If ELMA's own data
   is not reachable keyless, say so — that alone changes D-029(d).
4. **What `document_types` actually contains.** The identifiers a service group lists (`urn:oasis:names:…`,
   `urn:fdc:peppol.eu:2017:poacc:billing:01:1.0` and its Norwegian profile ids), how many a typical participant
   lists, and which one means "can receive an EHF invoice" — the fact D-029's `document_types` field exists to carry.
