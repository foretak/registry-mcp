## A. `core/models.py`

`LeiRecord` is **D-026(c)'s shape, unamended** — four fields plus `provenance` and `notes`:

```python
class LeiRecord(_Base):
    lei: str | None = None
    legal_name: str | None = None
    registration_status: str | None = None
    provenance: SourceRef
    notes: list[str] = []
```

and `CompanyReport.lei: LeiRecord | None = None`, always present per D-004, `null` on every lookup
that did not ask for it. Do not widen the model. In particular **do not add a field for GLEIF's
`entity.status`** — D-045(e) declines it by name.

Field descriptions must carry, in substance:

- **`lei`** — the 20-character Legal Entity Identifier GLEIF publishes for this entity. **`None`
  *inside a present block* means GLEIF holds no LEI for it**, which is a real and useful answer
  about a counterparty and is not the same as the block being absent (D-026(c), D-011). The LEI is
  **not** the EUID — `CompanyReport.euid`'s description already carries that distinction; point at
  it rather than restating it.
- **`legal_name`** — the legal name **as GLEIF publishes it**, which may differ from
  `CompanyReport.name` because they are two registers' opinions recorded at two moments. Carried
  verbatim, never reconciled, never used to correct the company record (D-018's rule: say which
  source said what).
- **`registration_status`** — GLEIF's `registration.status`, verbatim: `ISSUED`, `LAPSED`, … .
  National-vocabulary-in-values (D-042(g)). The description must say, in terms, that **a `LAPSED`
  LEI means the entity stopped renewing it and is not evidence of insolvency or inactivity** —
  Carillion plc (`03782379`) and Lehman Brothers International (Europe) (`02538254`) both read
  `entity.status: ACTIVE` beside `registration.status: LAPSED`, which is why this field carries
  the registration's status and not the entity's.
- **`provenance`** — a `SourceRef` whose `source` names GLEIF, `license` is `"CC0 1.0"`, and
  `source_url` is the record's own GLEIF URL. **Never imply endorsement and never describe
  `registry-mcp` as a GLEIF service** — D-026(c) records that GLEIF's anti-impersonation clause
  sits *outside* its data licence.
- **`notes`** — must always include the string that was actually sent as GLEIF's
  `entity.registeredAs` filter (see B2), so a `lei: null` is legible rather than silent.

## B. `core/registry.py`

### B1. `universal_includes`, and the three call sites

```python
universal_includes: ClassVar[frozenset[str]] = frozenset({"lei"})
```

on `Registry`, documented as: attachments whose upstream is not a national register and which every
country therefore declares by default; a country module adds nothing and edits nothing (D-045(e)).

**One helper, used by all three call sites — do not inline the union three times:**

```python
@property
def effective_includes(self) -> frozenset[str]:
    universal = frozenset() if self.id_may_be_personal else type(self).universal_includes
    return universal | self.supported_includes
```

The `id_may_be_personal` subtraction is **not optional and not a detail**. D-045(e): an attachment
that sends the identifier to a **third-party host in a URL query string** is not offered by a
registry whose identifiers can be a natural person's. Sweden sets that flag (D-040(a)), so Sweden
does not declare `lei`. Put the reason in the code comment, citing D-039's exposure category (URLs,
access logs, `Referer`) and D-041(g)'s limit (Bolagsverket's own second call was permitted because
it is the same host, the same TLS session and a POST body — GLEIF is none of those).

The three sites:

1. `lookup_with`'s validation — `unknown` is computed against `effective_includes`, and the
   `bad_request` `hint` and `details["allowed"]` list `sorted(effective_includes)`.
2. `country_info()` — `supported_includes=sorted(self.effective_includes)`.
3. The cross-country static test D-044(d) added —
   `test_every_declared_include_is_reachable_in_every_country`, which despite its subject lives in
   **`tests/test_client_gb.py` (~`:2629`)** — must read `effective_includes`, not
   `supported_includes`, or it will fail on `lei` having no country declaration. **Update that
   test, do not weaken it**: it must still prove that every declared include has both a method and
   a matching `CompanyReport` field, in every country. `lookup_with`'s own `RuntimeError`
   misconfiguration guard must union the same way, or a country declaring `lei` correctly would
   trip it.

### B2. The concrete `lei()` method

```python
async def lei(self, id: str) -> LeiRecord: ...
```

on `Registry` — concrete, not abstract, exactly as `lookup_with` is (D-042(b), D-028(5)'s
precedent). The ABC stays four abstract methods wide.

**The query. This is the one thing that is easy to get wrong, and D-045(e) measured it:**

- `filter[entity.jurisdiction]` = `self.country` (our own ISO code — free, and it removes any
  cross-country collision).
- `filter[entity.registeredAs]` = **`self.format_id(normalised_id)` if that is not `None`, else the
  normalised id**. This is an **exact string match on what the national register wrote**, not on
  what we normalise to:

  | | our normalised `id` | GLEIF `registeredAs` | bare-digit query | formatted query |
  |---|---|---|---|---|
  | NO Equinor | `923609016` | `"923 609 016"` | **0 hits** | 1 hit |
  | NO DNB | `984851006` | `"984 851 006"` | **0 hits** | 1 hit |
  | SE Ericsson | `5560160680` | `"556016-0680"` | **0 hits** | 1 hit |
  | GB Tesco | `00445790` | `"00445790"` | 1 hit | — |
  | GB NatWest Markets | `SC090312` | `"SC090312"` | 1 hit | — |

  Norway's and Sweden's `format_id` already produce GLEIF's exact strings; Britain does not
  override `format_id`, which is exactly what GLEIF wants. **Both candidates are tried — the
  formatted one first, the bare one only on zero hits** — and the block's `notes` name the string
  that was sent. Two queries at most, and the second only on a miss.
- Normalise the identifier through `self.validate_id(id)` first, as every other method in this
  codebase does, so an invalid id raises `invalid_id` before a request is made.
- **The URL brackets must be percent-encoded** (`filter%5Bentity.jurisdiction%5D`). If you probe
  with `curl`, pass `-g` or the shell/curl globbing will eat them and you will get a confusing
  empty result — that is a probing artefact, not a GLEIF behaviour.

**The registration-authority codes are asserted, never used as inputs.** Carry GLEIF's own
`entity.registeredAt.id` and `entity.registeredAs` into the block's `notes` (or leave them out
entirely — do **not** add model fields for them, D-026(c)'s shape is unamended), and pin the
observed values in a test:

| Country | RA code | What GLEIF calls it |
|---|---|---|
| NO | `RA000472` | Foretaksregisteret (**not** `RA000473`, which is Enhetsregisteret — our lookup reads Enhetsregisteret and GLEIF's records cite Foretaksregisteret; that is GLEIF's business, not a bug) |
| SE | `RA000544` | Bolagsverket |
| GB (England and Wales) | `RA000585` | Companies House |
| GB (Scotland) | `RA000587` | Companies House |
| GB (Northern Ireland) | `RA000586` | Companies House |

**A test that pins `RA000585` for "the UK" is wrong and will fail on every Scottish company.**

**Result handling.**

- `total == 0` → a **present** block with `lei=None`, `legal_name=None`,
  `registration_status=None`, a real `provenance`, and a `notes` sentence naming the string(s)
  queried. This is the answer, not an absence.
- `total == 1` → the record.
- `total > 1` → **not observed in any probe D-045(e) made**, so do not invent a tie-break. Take the
  first record, and append a `notes` sentence saying GLEIF returned more than one record for this
  registration number and naming how many and each `lei`. A silent pick is the failure this project
  exists to avoid; a disclosed one is honest. Report it if you ever see it live.
- Any transport failure, timeout or non-200 → raise `RegistryError(UPSTREAM_ERROR)`. `lookup_with`
  turns that into an **absent** block plus a `notes` sentence on the report, and **the lookup still
  succeeds** (D-042(b)) — you write no code for that, but you must test it.
- GLEIF needs **no credential**, so `requires_api_key` and `api_key_env` are untouched (D-026(c)).

`core/gleif.py` (new) holds the HTTP client, the base URL, the mapper and the cache read/write —
the same separation `registries/*/client.py` uses, one level up, because this upstream belongs to no
country. Keep `core/registry.py` free of `httpx` (`grep -n "httpx" src/registry_mcp/core/registry.py`
must stay empty).

## C. `core/cache.py` — the per-kind TTL table

D-026(c), D-028(2), D-041(h) and D-042(j) have all named this table and none has built it. Build it,
and **change no existing caller** — D-045(e) amends D-042(j) so that the kind is read from the key
rather than passed as an argument.

```python
#: kind -> (ok_ttl_seconds, empty_ttl_seconds). A kind absent from this table
#: falls through to today's behaviour byte for byte.
_TTL_BY_KIND: dict[str, tuple[int, int]] = {
    "lei": (7 * 24 * 3600, 24 * 3600),
}
```

- The kind is the **third `:`-separated segment** of the cache key, which D-006's convention already
  puts there: `GB:companies-house:charges:{crn}`, `NO:brreg:filings:{orgnr}`,
  `SE:bolagsverket:filings:{env}:{id}`. Parse it defensively — a key with fewer than three segments
  yields no kind and falls through.
- `_ttl_seconds(status, key)` reads the pair when the kind is in the table (`status == "not_found"`
  → the empty TTL, anything else → the ok TTL) and otherwise behaves **exactly as today**,
  including the `REGISTRY_MCP_CACHE_TTL_SECONDS` override and its warning on a non-int value.
- **A declared kind ignores `REGISTRY_MCP_CACHE_TTL_SECONDS`.** That is deliberate and the docstring
  must say why: it is D-028(2)'s hard rule arriving early — when `officers` gets a row at one hour,
  an operator tuning cache performance must not be able to silently extend personal-data retention.
  Write that sentence, so the next reader adds a row rather than a second mechanism.
- **Do not migrate the five sites that fake a per-kind TTL with `status="not_found"`**
  (`registries/gb/client.py` ×3, `registries/se/client.py`, `registries/no/client.py`). They are
  outside your footprint, two other tasks hold those files this round, and D-045(e) rules that none
  of them needs to change: the kind is already in their keys and the table's fall-through reproduces
  their current numbers exactly. Assert that fall-through in a test.
- **The 24 h empty TTL for `lei` is not D-006's 1 h and that is deliberate** (D-045(e)): nothing
  statutory, time-critical or credit-bearing turns on an entity acquiring an LEI, and re-asking a
  free service hourly for an answer that is "no" for most of the world's companies points the harm
  the wrong way. Put the reason in the comment.
